OpenBench

A from-scratch benchmark that asks one question and tries to answer it honestly: given the same underlying model, how much does the harness around it change the result?

A coding agent is two things bolted together: a model that predicts tokens, and a harness — the CLI that wraps it in a run loop, a tool set, a permission policy, and the context it feeds back in (codex, pi, opencode, cursor, devin, and open-model claude). We talk endlessly about the model and rarely measure the harness. OpenBench measures the harness.

The thesis in one line On correctness, frontier harnesses on a frontier model are indistinguishable — they all just solve the task. Where they separate is efficiency: wall-clock time (up to ~4×) and, more sharply, tokens spent per solved task (up to ~8×). Saturation is the premise, not a failure — it's what pushes the measurement onto the axis that actually varies: cost-per-solve and speed-per-solve.

Everything is Python 3 standard library only, runs locally, and every run appends one JSON line so results are auditable after the fact. No Harbor, no inspect_ai — building the measurement apparatus by hand was the point, because a benchmark is only worth its verification discipline.

At a glance

What it grades

Self-contained coding tasks run headlessly by real agent CLIs.

Who decides success

A checker script — exit 0 = solved. Never the harness's own claim.

What separates harnesses

Not correctness (it saturates). Wall-time and tokens-per-solve.

How results are stored

Append-only JSONL, one row per task × harness × trial cell. Resumable.

Statistical honesty

Wilson 95% intervals, not point estimates. Overlap = not yet resolved.

Negative control

A null harness that does nothing — every checker must fail it.

The run pipeline

Everything flows through bench/run.py. For each cell — one (task, harness, trial) triple — the runner executes this exact sequence. The green box is the only authority on success.

01

Copy workspace

Pristine workspace/ → disposable temp dir. Source is never touched.

→
02

Invoke adapter

Import adapters/<h>.py, call run() headlessly with cwd = temp dir.

→
03

Run checker.sh

The judge. cwd = temp dir, TASK_DIR set. Exit 0 = solved.

→
04

Classify + append

Failure class computed, one JSON row appended to results.jsonl.

Then bench/report.py reads that log and aggregates it into per-harness tables. Two more tools bracket the loop: validate_tasks.py proves every checker is honest before a run, and bench/doctor.py preflights each harness's CLI/auth without spending tokens.

The key invariant The adapter reports completed (the CLI exited cleanly). That is not task success. Success is decided only by re-running the world through checker.sh afterward. This separation is what lets the benchmark catch a harness that claims victory but didn't actually fix the code.

Five load-bearing ideas

If you understand these five, you understand why the numbers can be trusted. Each one closes a specific way a benchmark can silently lie.

1. The checker is the sole judge — and it's validated

Success is checker.sh exit 0, full stop. But who checks the checker? validate_tasks.py proves each one is correctly polarized by running it twice:

  • Against a fresh untouched workspace → it must FAIL (else the task is scored solved before the agent does anything).
  • Against the workspace with solution/ overlaid → it must PASS (else a correct answer would be rejected).

This catches the two ways a grader lies about difficulty. It's also why expected outputs for data-driven tasks are generated from the golden solution, not hand-written — the checker owns its oracle.

2. The null control

A built-in null "harness" does nothing and reports completed=True. Because it never edits the workspace, every checker must fail it. A nonzero null score would mean a broken, too-lenient checker. It uses zero tokens and is the benchmark's smoke test for the whole grading apparatus.

3. Fresh workspace per run

Every cell gets an untouched copy of the task workspace in a temp dir that's deleted afterward. Runs cannot contaminate each other or the source tree — a finally: shutil.rmtree(workdir) guarantees it even on crash.

4. Wilson intervals, not point estimates

With a handful of trials, "2/3 = 67%" is noise. Every success rate is reported with a Wilson 95% confidence interval, and two harnesses are treated as different only when their intervals separate. Overlap means "not yet resolved." (Wilson over the naïve formula because it stays inside [0,1] and behaves sensibly at 0/n and n/n.)

5. Resumability & auditability

Each cell's identity is a deterministic run_id = harness:task:model:trialN. A cell whose run_id already appears in the log is skipped, so you can stop and re-run freely (--force overrides). Every row records the exact cmd executed. One line, one cell, forever appendable.

Two result framings

Track A — same model, harness varies

Every compatible harness is pinned to the same canonical model, gpt-5.5-medium, so any difference comes from the harness — scaffolding, tools, prompting, permissions — not the model. This is the controlled experiment. Uses subscription/OAuth logins.

Open-model panels

Open models (glm-5.2, deepseek-v4-flash, kimi-k2.7-code, glm-4.7-flash) run through adapters that reach the providers directly via first-party API keys. Answers "how close are open models to frontier, and at what cost?"

Honest caveats baked into the framing devin is flaky in the latest analysis and excluded from M4.5 rankings. cursor/devin have closed model menus (no open models). claude is open-model-only by design — a run can never accidentally bill an Anthropic subscription. codex can only reach open models through the local Responses↔Chat bridge (bench/openmodel_bridge.sh).

Anatomy of a task

A core task is a directory under tasks/<name>/. Imported tiers live under tasks-imported/<collection>/ and run with --tasks-dir tasks-imported.

tasks/make-ci-green/
├── instruction.md   what the harness is told (reads as a normal engineering request)
├── workspace/       starting files; copied fresh into a temp dir every run
├── checker.sh       grades the result; exit 0 = solved, may print SCORE: for partial credit
├── solution/        golden files — used ONLY by validate_tasks.py, never shown to the agent
└── checker_data/    optional: inputs/expected outputs the checker owns (kept out of workspace/)

Three rules the runner honors for every cell:

  • The source is sacred. workspace/ is copied to a disposable temp dir; the source under tasks/ is never modified.
  • Checkers reference their own data absolutely. checker.sh runs with cwd = temp workspace copy and env TASK_DIR = absolute task dir, so it reads $TASK_DIR/checker_data/... regardless of cwd.
  • No leakage. Instructions never mention the checker, the solution, or that this is a benchmark. They read like a real ticket.

There are three tiers, each reported and scored separately:

TierLocationWhat it is
Core synthetictasks/8 repo-authored tasks incl. partial-credit hard ones (make-ci-green, add-feature, misleading-error).
Exercismtasks-imported/exercism/11 MIT-licensed spec tasks with per-task provenance.
Terminal-Benchtasks-imported/terminal-bench/5 Apache-2.0 TB tasks — the new frontier tier, run through the Docker lane.

Adapters & the contract

Each harness is one module bench/adapters/<name>.py. The runner imports it dynamically and calls a single function. The full contract is bench/ADAPTER_SPEC.md; the essence:

NAME: str                # canonical harness name, matches filename
MODELS: dict[str, str]   # canonical model name -> harness-specific model string

def run(instruction, workdir, model, timeout_s) -> dict:
    # - map canonical `model` -> harness flags via MODELS
    # - run the CLI HEADLESSLY, cwd=workdir, never prompt interactively
    # - enforce timeout via subprocess (macOS has no `timeout` command)
    # - the agent's edits must land in workdir
    return {
      "completed": bool,       # CLI exited 0 within timeout — NOT task success
      "error": str | None,     # timeout / crash / unsupported-model reason
      "output_tail": str,      # last ~2000 chars of stdout+stderr
      "tokens": int | None,    # if the harness reports usage
      "turns": int | None,     # model rounds, if reported
      "cmd": list | str,       # what ran (for the audit log)
      "full_output": str,      # OPTIONAL: untruncated — becomes the local transcript
    }
Auth quirks live inside the adapter The user's real config files are never modified — read-only use only. Each adapter isolates itself so the benchmark's needs never leak into your personal setup.
HarnessFrontier pinAuth isolation
codexgpt-5.5, reasoning_effort=mediumExisting login; open models via the foreground bridge.
pigpt-5.5 --thinking mediumIsolated temp HOME with only .pi/agent/auth.json copied in + --no-extensions, so personal extensions never load (one of them crashes headless mode).

Worked example — how pi counts tokens. pi's --mode json emits a JSONL event stream; the adapter parses the final agent_end message list and sums input+output over assistant messages only (cache re-reads excluded, so it's fresh tokens — matching the other adapters). Turns = the count of turn_end events. Parsing is defensive: any shape drift yields tokens=None rather than a wrong number. Open models are wired in by writing a tiny JS provider extension into the isolated HOME and loading it with -e.

Local vs Docker execution

The same adapter module runs unchanged in both modes — the container only adds isolation.

--exec local default

Runs on the host. Fast, fine for core & Exercism tasks on a laptop. No GPU needed.

--exec docker

Each cell runs in a fresh disposable docker run --rm container built from bench/docker/. Used for Terminal-Bench (agent shell commands need isolation).

Key design points of the Docker lane (bench/docker_exec.py + bench/entry.py):

  • Auth is mounted read-only at runtime, never baked into the image — so the image is safe to share/rebuild. entry.py copies mounted auth into a writable $HOME for CLIs that must write their config home.
  • Graceful fallback. If the daemon or image is unavailable, the runner falls back to local and records the actual exec_mode — unless --no-docker-fallback is set.
  • Partial image. codex, pi, and open-model claude are installed and version-checked; opencode/cursor/devin are behind --build-arg INSTALL_UNVERIFIED=true — use --exec local for those.
  • Container cleanup is guaranteed on every exit path (a recent hardening — a hung container is hard-killed after timeout_s + grace).

Scoring & partial credit

A checker exit code is binary, but a checker may also print a SCORE: line to grade partial progress — essential for hard tasks where "did it get 4 of 6 bugs?" is the interesting signal.

Checker outcomesuccessscore
Exit 0true1.0 — a full pass; a SCORE: line can't lower it.
Nonzero exit, with SCORE: 0.47false0.47 — partial credit (last parseable line wins, clamped to [0,1]).
Nonzero exit, no SCORE:false0.0
Checker timeoutfalse0.0

SCORE: is optional and backward compatible: a checker that never prints one behaves exactly as before. The mean score (averaged over all trials, including failures) is the discriminating number for partial-credit tasks — that's what separates a 0.47 model from a 1.0 model when raw pass/fail can't.

Reporting & Wilson intervals

bench/report.py reads the JSONL log and prints, per harness: per-task success (x/n), overall success + Wilson 95% CI, mean score, mean wall-clock, tokens-per-solve, and mean turns. --efficiency prints the harness-tax view alone.

Why "per solve", not "total" Efficiency metrics are normalized per solved task, so they measure the cost of getting a result rather than a running total that just scales with the trial count. Token/turn data is optional per adapter: a harness that reports none shows -, never silently counted as zero. 
harness  fix-failing-test  make-it-run  overall   wilson95        mean_s  tok/slv
-------  ----------------  -----------  --------  --------------  ------  -------
null     0/1               0/1          0/2 (0%)  [0.000, 0.658]  0.00    -

Reading the interval: with few trials it's wide (3 trials can span most of 0–100%), so overlapping intervals mean the harnesses are not distinguishable yet; it shrinks as trials grow.

The self-auditing failure taxonomy

This is the piece that makes OpenBench trustworthy rather than merely functional. Every non-solved cell is classified at write time (bench/failure_class.py) into one of five classes, using the adapter's full untruncated output:

ClassMeaningCounts toward solve rate?
solvedChecker exit 0.yes
wrong_answerGenuine capability miss — agent tried, checker rejected.yes
timeoutChecker timeout, or wall-clock rode the cap (≥98%).yes
rate_limitedProvider 429 / daily-token exhaustion (needs API-error context, not just the digits "429").EXCLUDED
infraDocker unavailable, missing auth, no result sentinel, image not found…EXCLUDED
Why this matters A rate_limited or infra failure is not a capability failure — counting it as one would make a fully-capable model look broken. Excluding those classes from the denominator is what separates a model claim from an infrastructure artifact. The rate-limit detector deliberately requires provider/API-error context so a task that merely mentions "HTTP 429" isn't misclassified. A backfill_failure_class.py tool re-classifies old rows (weaker, since it only has saved fields).

Transcripts & the scrubber

Alongside each results row, the runner writes that cell's full agent transcript to transcripts/<results-stem>/<run_id>.txt. These are raw, unscrubbed harness output and can contain home paths, usernames, hostnames, email, or secrets the agent echoed.

Hard rule Transcripts are never published as-is. transcripts/ is gitignored and there is deliberately no publishing path in the repo. Before sharing, run bench/scrub.py --check (reports potential PII), then bench/scrub.py --out scrubbed/ (writes scrubbed copies, originals untouched), then re-check. It over-redacts on purpose — a false positive is cheap, a leaked secret is not.

The findings arc

The milestones tell a single story: correctness saturates, so the interesting signal moves to efficiency and to the open-model frontier. Committed datasets live under data/; analyses in RESULTS.md.

M3 — correctness saturates; speed separates ~4×

3 easy tasks × 5 harnesses × 5 trials. Every harness solved every task: 15/15, identical Wilson intervals. Only null separated (confirming the checkers discriminate). But mean wall-time per solve ran pi 16.4s → opencode 62.7s — ~3.8×. A saturated correctness table isn't a null result; it's a baseline that points at the axis that varies.

M3.5 — the token tax spans ~8×

Token accounting wired into every adapter. Tokens-per-solve: pi 5.3k → codex 42.5k. Crucially, the token ranking is not the time ranking — opencode and codex finish in about the same wall-clock but codex spends ~2× the tokens. Wall-clock and token-tax are genuinely different axes.

M4.5 — even a 6-bug task can't separate frontier harnesses

Three genuinely harder partial-credit tasks (6-bug CI fix, config parser with @include, misleading traceback). Four clean harnesses each scored 9/9, mean-score 1.0. Calibrating difficulty for the frontier is hard. Efficiency separated again. These saturated tasks became the frontier baseline for the next step.

M4 — three of four open models reach frontier parity, for ~$1.02

The tasks that couldn't crack the frontier were the perfect probe for weaker models. Mean score via pi: glm-5.2 = 1.00, deepseek-v4-flash = 1.00, kimi-k2.7-code = 1.00, glm-4.7-flash = 0.47. Three of four match GPT-5.5-medium on real coding tasks; only the free small model drops — with genuine partial credit, exactly where the design was built to bite. The whole 72-cell matrix cost ~$1.02. And pi won or tied every model column — a model-agnostic harness-quality effect.

Terminal-Bench — the new frontier tier

The task factory got swept: synthetic bug-fix/spec tasks at 7–8k lines still scored ~1.0 for frontier-parity agents — "bigger codebase is harder" is false. So the roadmap forked to importing proven-hard Terminal-Bench tasks (45 cells: 3 harnesses × 5 tasks × 3 trials, landing at 12/15, mean 0.80 — finally below the synthetic ceiling) plus performance/complexity-budget tasks with partial credit designed in.

Why it's trustworthy: the incidents were the methodology

The most durable finding is a process one. Twice, a per-cell look at the raw data overturned a headline the summary numbers implied. Both saves came from the failure taxonomy above — not from cleverness.

devin's "8/9"

A summary said devin scored 8/9 with one "genuine miss." The per-cell taxonomy said: two 900s hangs, one nonzero-exit-that-passed, and the "miss" was an instant 0.99s crash (an adapter regression, not a model attempt). Token counts were internally inconsistent by ~20×. devin wasn't 8/9 — it was flaky, and was pulled from every ranking.

opencode's "2× harness gap"

glm-4.7-flash scored 0.47 via pi but 0.22 via opencode — a dramatic harness×model interaction? No: 8 of 72 cells were the same adapter bug (a bytes + str crash on every 900s timeout), and opencode was 5–8× slower so it hit the wall constantly. The gap was infrastructure, not capability (kimi:pi = 1.00 proves the model is capable). Excluded the 8 cells, reported both ways, filed the bug.

The rule that caught both Classify every cell — pass / partial / timeout / adapter-exception / rate-limited — before you trust a block-level average. For a benchmark whose whole value is trustworthiness, that per-cell discipline isn't a chore around the science. It is the science.

Glossary

HarnessThe CLI wrapping a model: run loop, tools, permissions, context management. The thing under test.
CellOne (task, harness, trial) run. Identity = run_id. One JSONL row.
Checkerchecker.sh — the sole judge of success. Exit 0 = solved; optional SCORE: for partial credit.
completed vs successcompleted = the CLI exited cleanly (self-reported). success = the checker said so. They are different on purpose.
null controlA harness that does nothing; must fail every checker. Guards against too-lenient graders.
Wilson interval95% CI on a success rate that behaves well for small n and at 0/n, n/n. Overlap = not distinguishable.
tokens-per-solveTotal reported tokens ÷ solves. The "harness tax" in the currency that costs money.
Track ASame-model framing (all harnesses on gpt-5.5-medium) — isolates the harness variable.
Failure classOne of solved / wrong_answer / timeout / rate_limited / infra. The last two are excluded from solve rate.
SaturationWhen frontier harnesses all score 1.0 — the premise, not a failure. Pushes measurement onto efficiency.
